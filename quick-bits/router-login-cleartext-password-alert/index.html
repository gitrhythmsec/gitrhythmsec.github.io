A Router Login Triggered a Cleartext Password Alert

Status: InvestigatingNovember 17–18, 2026

What I Saw

I logged into my GL-iNet router's admin panel and immediately noticed a Priority 1 alert pinned in red on WatcherDash. The signature was ET INFO Http Client Body contains pwd= in cleartext (SID 2012888). Since I'd just entered an admin password, the timing was hard to ignore.

Investigation

I inspected the alert instead of assuming that Priority 1 meant an intrusion. WatcherDash showed traffic from my Windows workstation to the router, with several occurrences of the same signature.

I opened Firefox Developer Tools and examined the network request made by the login form. It was an HTTP POST with a form field named pwd, and Developer Tools displayed the submitted value in readable text. I hadn't deliberately chosen an insecure connection: entering the router's IP address in my browser took me to the http:// admin page rather than HTTPS. That meant the original login request did not have HTTPS transport encryption.

I repeated the login using a dummy password, which let me confirm the form's behavior without exposing my real credentials in screenshots. I also opened the admin page using https://. Firefox still displayed the form value in Developer Tools, but that's expected: the browser can inspect its own request before TLS encrypts it.

I then compared the IDS behavior directly. Logging in over HTTPS produced no matching Suricata alert, while switching back to HTTP caused SID 2012888 to fire immediately. This was a useful practical check that the alert depended on Suricata being able to inspect the unencrypted request body. It did not, by itself, establish that HTTPS was being enforced or replace packet-level verification.

What It Turned Out to Be

The alert matched the router administration workflow: a pwd= form field was sent in a cleartext HTTP request body during a login attempt. That explains the Suricata detection without implying that an attacker was present.

The HTTP-versus-HTTPS test showed that the alert stopped when I used HTTPS and returned immediately over HTTP. That is consistent with the request body being protected by TLS on the HTTPS connection, but it isn't yet the same as verifying enforcement. At the time of writing, I still plan to review the router's HTTPS/security settings and confirm with a packet capture that login credentials are no longer readable on the wire or accepted over plain HTTP.

Why It Mattered

This is the kind of alert I built my IDS to notice. I correlated a detection with something I had just done, found the corresponding request in the browser, reproduced the behavior safely, and compared alerting over HTTP and HTTPS. It also highlighted an important distinction: plaintext in Developer Tools is not the same thing as plaintext on the network when HTTPS is enabled. The remaining job is to validate the secure configuration, not just assume the warning is gone.
