Hardware / Networking

Building a Network Scanner with an Arduino Uno

By Colton H.Status: Completed

The hardware has since been disassembled; this write-up documents the completed experiment.

I originally started this project as a way to learn some basic electronics with an Arduino Uno and a 16×2 LCD screen. I occasionally want to find devices on my home network, and I had an Arduino Ethernet Shield 2 on my desk, that I didn’t know what to do with. That led to a simple question: could I use an Arduino to connect to a network and display the IP addresses of devices that are alive?

As it turns out, the answer is yes — although the project also demonstrated why an Arduino Uno is not exactly an ideal network scanner.

Hardware

The project used three main components:

  • Arduino Uno
  • Arduino Ethernet Shield 2
  • 16×2 LCD with an I²C backpack

The LCD was connected using I²C:

Arduino UnoLCD
5VVCC
GNDGND
A4SDA
A5SCL

The I²C address of the display was 0x27.

One useful feature of the Ethernet Shield 2 is that its headers pass the Arduino's pins through the shield. This allowed the shield to be mounted directly on top of the Uno while the LCD remained connected through A4 and A5.

The LCD uses I²C, while the Ethernet Shield communicates with the Uno through SPI, so the two devices can coexist without interfering with each other.

The Ethernet Shield 2 contains a W5500 Ethernet controller. On the Arduino Uno, the shield uses the SPI interface along with digital pin 10 as its chip-select pin.

Establishing Network Connectivity

The first goal was simply to verify that the Arduino could communicate with the network while the LCD was connected.

Using the Arduino Ethernet library, the Arduino requested an address from the network's DHCP server. Once DHCP completed, the assigned IP address was displayed on both the LCD and Serial Monitor.

An early successful test displayed an address similar to:

Ethernet OK!
192.168.8.232

Later DHCP requests assigned a different address, such as:

192.168.8.205

This was expected because the Arduino was using DHCP rather than a static address. The successful DHCP test confirmed that the LCD, Uno, Ethernet Shield, SPI interface, and network connection were all functioning at the same time.

Deciding How to Discover Hosts

There are several ways to determine whether another device exists on a local network. Two particularly interesting options were ARP and ICMP.

ARP is used on a local IPv4 network to determine which MAC address corresponds to an IP address. This makes ARP particularly useful for finding devices on the same local network, including some hosts that may refuse to respond to ICMP.

ICMP is the protocol used by traditional ping commands. A scanner can send an ICMP Echo Request to an address and mark the address as alive if an Echo Reply is received.

For this experiment, I decided to begin with ICMP because there was already an Arduino library capable of generating ICMP Echo Requests through the W5500.

Software and Library Problems

This turned out to be one of the more interesting parts of the project.

My original Ethernet test used version 2.0.2 of the standard Arduino Ethernet library:

#include <Ethernet.h>

However, the W5500 ICMP library I found was written for another library named Ethernet2:

#include <Ethernet2.h>
#include <ICMPPing.h>

Initially, I attempted to use the standard Ethernet library along with ICMPPing.

That produced a long list of compiler errors such as:

redefinition of 'class EthernetClient'
redefinition of 'class EthernetServer'
redefinition of 'class EthernetUDP'
redefinition of 'class DhcpClass'
redefinition of 'class EthernetClass'

The cause became clear after looking at the include chain.

My sketch was loading:

Ethernet.h

while ICMPPing.h was internally loading:

Ethernet2.h

Both libraries defined classes with names such as EthernetClient, EthernetServer, and EthernetUDP. The compiler therefore encountered two completely different definitions for the same classes.

The solution was to use the Ethernet2 library expected by the ICMP library rather than loading both Ethernet implementations simultaneously.

The Chip-Select Problem

After fixing the library conflict, the example ICMP program still did not initially obtain an address through DHCP.

The example code contained:

#define ETH_CS_PIN 8
#define ETH_RST_PIN 7

and its documentation stated:

Ethernet CS pin to pin 8
Ethernet reset pin to pin 7

That configuration was intended for the hardware used by the library author and did not match my Arduino Ethernet Shield 2.

The Ethernet Shield 2 uses digital pin 10 as the W5500 chip-select pin.

Changing:

#define ETH_CS_PIN 8

to:

#define ETH_CS_PIN 10

immediately solved the problem.

The Arduino successfully obtained a DHCP address and began sending ICMP Echo Requests. This was a useful lesson that even when two pieces of hardware use the same controller, example code may not work with how that controller is physically connected.

Successfully Pinging a Device

The first target was my gateway:

192.168.8.1

The Arduino successfully received the ICMP replies.

Once a single host could be pinged, I modified the program to loop through a small range of addresses.

For example:

192.168.8.150
through
192.168.8.160

My phone happened to be using:

192.168.8.156

The resulting output looked like:

Pinging 192.168.8.155 ... no response
Pinging 192.168.8.156 ... ALIVE! 129 ms
Pinging 192.168.8.157 ... no response

Repeated scans showed the phone responding in approximately 129–130 ms, although one response took approximately 220 ms. At this point, the Arduino was functioning as a legitimate ICMP network scanner!

Automatically Discovering the Network

The next step was removing the hard-coded network address, and setting network information automatically. DHCP provides more than just the IP address. It also provides information such as the subnet mask and default gateway.

The scanner retrieved:

Arduino IP: 192.168.8.205
Subnet mask: 255.255.255.0
Gateway: 192.168.8.1

The program then calculated the network address by performing a bitwise AND between the IP address and subnet mask.

In this case:

IP:       192.168.8.205
Mask:     255.255.255.0
                     ↓
Network:  192.168.8.0

It also calculated the broadcast address:

Broadcast: 192.168.8.255

Because this was a /24 network, the Arduino could then scan the usable host addresses:

192.168.8.1
192.168.8.2
192.168.8.3
...
192.168.8.254

The program skipped its own DHCP address rather than trying to ping itself, in an attempt to save time.

The Full Network Scan

The final experiment was scanning the entire /24.

The scanner began with:

Network: 192.168.8.0
Broadcast: 192.168.8.255

It eventually found three devices responding to ICMP:

192.168.8.1   ALIVE   1 ms
192.168.8.172 ALIVE   3 ms
192.168.8.231 ALIVE   3 ms

The Arduino itself occupied:

192.168.8.205

and was skipped.

Interestingly, the phone at 192.168.8.156, which had responded consistently during the earlier targeted scan, did not respond during the full scan.

This demonstrated an important limitation of ping-based discovery:

No ICMP response does not necessarily mean that no device exists at that address.

Devices can ignore ICMP, filter it with a firewall, enter power-saving states, or otherwise fail to respond even though they are connected to the network.

An ARP-based scanner would potentially detect some of these devices because ARP operates at a lower layer and is necessary for normal IPv4 communication on the local network.

The Arduino's Biggest Limitation: Speed

The full scan revealed the biggest problem with using an Arduino Uno as a network scanner. It took approximately 27 minutes. The problem was not Ethernet bandwidth, but it was in how the scan was done. The Arduino was performing the scan sequentially:

Ping .1
wait for response or timeout

Ping .2
wait for response or timeout

Ping .3
wait for response or timeout

...

Ping .254
wait for response or timeout

Responsive devices were fast. The gateway answered in approximately 1 ms, while other wired or active devices responded in around 3 ms.

Addresses with no hosts were the problem. For every address that did not respond, the Arduino had to wait for the ICMP operation to time out before retrying three times, then proceeding to the next IP address.

Because almost all 254 possible addresses were unused, most of the 27-minute scan consisted of the Arduino waiting for nonexistent hosts.

A desktop operating system or Linux device can perform this job very differently. Tools such as Nmap can have many probes outstanding simultaneously rather than waiting for each individual address before beginning the next one.

Conceptually, the Arduino was doing:

Host 1  -> wait -> Host 2 -> wait -> Host 3 -> wait

while a more capable system can behave more like:

       -> Host 1
       -> Host 2
Scanner-> Host 3
       -> Host 4
       -> Host 5

and process responses as they arrive.

The Arduino Uno also only has a 16 MHz 8-bit AVR processor and 2 KB of SRAM. Those limitations make sophisticated asynchronous networking, large host tables, hostname resolution, service detection, and similar functionality increasingly difficult.

It is possible to optimize the Arduino scanner, reduce timeouts, or build more complicated logic, but eventually it becomes an exercise in working around the limitations of the platform, when far simpler methods exist.

Was the Arduino the Wrong Tool?

For building a practical network scanner, probably. As a project to learn about network basics and demonstrate hardware usage, absolutely not!

The original goal was to learn basic electronics and put an ethernet shield to use, and using the Arduino forced me to interact with several layers that would normally be hidden by an operating system.

Along the way, I encountered hardware pin assignments, SPI chip selection, DHCP, subnet masks, network-address calculations, ICMP Echo Requests, library dependencies, compiler conflicts, and the practical consequences of network timeouts.

A Linux computer could easily accomplish the final network scan with a single command, but doing it on an Arduino made the individual components and mechanics much more visible.

Moving to a Raspberry Pi

The logical next version of this project is to move the scanning functionality to a Raspberry Pi Zero 2 W. The Pi can control the same 16×2 display using its I²C interface while using Linux networking tools to perform the actual discovery. That would make it practical to perform ARP discovery, ICMP scanning, hostname resolution, MAC-address collection, and potentially service detection in a fraction of the time.

The LCD could then provide a small physical interface:

NETWORK SCAN
12 HOSTS FOUND

followed by individual results:

HOST 3 / 12
192.168.8.172

Buttons could be added to scroll between discovered hosts or initiate another scan.

Conclusion

The Arduino network scanner ultimately worked. It successfully obtained its network configuration through DHCP, calculated its local network, generated ICMP Echo Requests, detected responsive hosts, measured response times, and scanned an entire /24 network. It was just painfully slow. The 27-minute ping scan made a strong case for why network scanning is usually performed by systems capable of handling many concurrent network operations. However, that limitation was arguably one of the most valuable results of the experiment. Instead of simply running a network-scanning utility, the project exposed many of the lower-level components involved in discovering another computer on a network. In the future I could get an ethernet hat for a Pi Zero, connect a screen, and actually make the tool, but for now this simple experiment is successful!
