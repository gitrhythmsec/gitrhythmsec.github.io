Self-Hosting UniFi Network Management on a Raspberry Pi 5

By Colton H.Status: Completed

Overview

I wanted to get hands-on experience with managed switches and network management in my home lab. Until this project, most of the switches I had used personally were unmanaged devices where the only real configuration was deciding what cable went into what port.

I picked up a Ubiquiti UniFi Lite 8 PoE switch as a relatively inexpensive way to start working with managed switching concepts such as port configuration, PoE management, VLANs, port profiles, and network segmentation.

Rather than buying a dedicated UniFi CloudKey or gateway, I decided to self-host the UniFi management software on hardware I already owned.

The final setup uses a Raspberry Pi 5 running Ubuntu Server 24.04 LTS and UniFi OS Server to manage the switch.

Hardware and Network Layout

The main components are:

  • Raspberry Pi 5
  • Ubiquiti UniFi Lite 8 PoE
  • GL.iNet GL-AR750S router
  • Existing Ethernet connection to the rest of the network

The basic network path is:

Upstream Network
       |
GL.iNet Router
192.168.8.1
       |
UniFi Lite 8 PoE
192.168.8.2
       |
Raspberry Pi 5
192.168.8.3

The GL.iNet remains the router and firewall for the lab, while the UniFi switch handles Layer 2 switching and managed-port functionality.

Choosing a UniFi Controller

UniFi switches do not rely on a traditional standalone web interface for their full management experience. Instead, devices are adopted into a UniFi controller.

Ubiquiti sells dedicated hardware for this purpose, but UniFi OS Server can also be self-hosted.

I already had a Raspberry Pi 5 available, so using it as the controller gave me an opportunity to learn more about both UniFi and Linux-based infrastructure without buying another appliance.

The First Installation Attempt

My first attempt was to install UniFi OS Server on an existing Ubuntu 22.04 server.

The installer immediately exposed a compatibility problem:

Installed podman version 3.4.4 is below
the required minimum version 4.3.1

Ubuntu 22.04's available Podman package was too old for the version of UniFi OS Server I was trying to install.

I considered upgrading that server, but it already hosted other services and I did not want to introduce unnecessary changes just for the UniFi controller.

Reusing the Raspberry Pi 5

The Raspberry Pi 5 had previously been running Debian 12.

I initially explored upgrading that installation in place, but the proposed Debian major-version upgrade involved more than a thousand package changes along with Raspberry Pi-specific kernel, GPIO, camera, and desktop packages.

Since the Pi contained very little that could not easily be recreated, I decided that a clean installation was a better solution.

I preserved the original SD card rather than overwriting it and installed Ubuntu Server 24.04 LTS ARM64 on a separate card.

This also gave me an easy rollback option if I later discovered something important on the old installation.

Installing UniFi OS Server

Once Ubuntu Server was running, I installed the required Podman runtime and downloaded the ARM64 UniFi OS Server installer.

The installer configured UniFi OS Server as a systemd service.

After installation, the service could be verified with:

systemctl status uosserver

The resulting service was enabled and running automatically at boot.

I then accessed the locally hosted UniFi interface through a browser, created the management account, and allowed the controller to discover the Lite 8 PoE switch.

The switch appeared automatically and was adopted into the controller.

Cleaning Up the Pi's Network Configuration

The Pi initially had both Ethernet and Wi-Fi active on the same subnet.

The routing table contained two default routes:

default via 192.168.8.1 dev eth0 metric 100
default via 192.168.8.1 dev wlan0 metric 600

Linux correctly preferred Ethernet because it had the lower route metric, but having two interfaces on the same management network was unnecessary for an infrastructure server.

I removed the Wi-Fi configuration from Netplan and left Ethernet as the Pi's only local-network interface.

Tailscale remains installed separately for remote access.

Organizing Infrastructure Addresses

I also wanted the infrastructure devices to have predictable addresses.

Rather than configuring static addresses directly on each device, I used DHCP reservations on the GL.iNet router.

The resulting layout is:

192.168.8.1    GL.iNet router/firewall
192.168.8.2    UniFi Lite 8 PoE
192.168.8.3    Raspberry Pi / UniFi OS Server

Normal DHCP clients begin at .100, leaving the lower portion of the subnet available for infrastructure.

This keeps the configuration centralized while still allowing the devices themselves to use DHCP.

What I Learned

The project gave me practical experience with several concepts that are easy to understand theoretically but much more useful to see operating together.

I worked with:

  • Managed switching
  • UniFi device discovery and adoption
  • Self-hosted network management
  • PoE-capable switching
  • DHCP reservations
  • Linux route metrics
  • Netplan network configuration
  • systemd service management
  • Podman
  • ARM64 software compatibility
  • Separating network management from packet forwarding

One useful distinction was understanding that the UniFi controller is part of the management plane, not the traffic path itself.

The Raspberry Pi does not sit between devices passing traffic through the switch. If the controller is temporarily unavailable, the switch continues forwarding traffic using its existing configuration.

Current State and Next Steps

The UniFi Lite 8 PoE is now adopted and managed by the Raspberry Pi 5, and the controller runs automatically as a persistent service.

For now, I am keeping the switching configuration relatively simple.

Future work may include VLANs, port profiles, management segmentation, port mirroring, and more advanced firewall policy.

I plan to explore several of those topics as part of a separate Suricata IDS/IPS project, where the managed switch can provide traffic visibility and segmentation for security monitoring.
